Lab 6 · Deploy
Deploy to OpenShift
Manual deploy to validate the cluster before automating with CI/CD
Prerequisites
✅ Before You Start
  1. Lab 3 completed, so you have the payment-app-java17 project (with its infra/ files) open in the Bob IDE.
  2. Access to a live OpenShift cluster: your instructor will provide access (a shared login).
  3. Your assigned namespace suffix (for example bob-1), given to you by your instructor. The deploy script creates deploy-test-<suffix> for you; everyone shares the same login, so using your own assigned suffix is what keeps your work separate from everyone else's. Use it consistently throughout this lab.
  4. The oc CLI installed, plus a login token for your cluster. This is the only local tool you need: no Docker, Podman, or Java required, since the image builds on the cluster. The oc CLI runs the same on macOS, Windows, and Linux. Need it? See Install the oc CLI.
💬 OVERVIEW
  • Before we automate anything, we deploy manually first. This is intentional: it lets us validate the cluster setup, catch security context issues, and confirm the app actually runs before a pipeline ever touches it.
  • We build the image on the cluster, not on your laptop. OpenShift builds it server-side from the existing Dockerfile, so the workflow is identical whether you're on an Intel Mac, an Apple Silicon Mac, Windows, or Linux. No Docker, Podman, or local Java needed: just the oc CLI.
  • Bob generates the deployment steps. We run them, watch what happens, and fix any issues together, live, with Bob's help. This is where real-world problems get solved.
Step-by-Step
1
Ask Bob to generate the deployment steps
As in the earlier labs, write the prompt as a Markdown file in the workspace, then hand that file to Bob. It asks Bob for the oc commands to build the image on the cluster from the existing multi-stage Dockerfile and deploy the app into your own namespace. Because the build runs server-side, the same commands work on any operating system.
  1. Create the prompt file. In the Explorer panel, create a New File named deploy-openshift.md, paste the prompt below into it, and save (⌘S / Ctrl+S).
    Prompt · Generate Deployment Steps
    ▼
    Before giving me any commands, ask me for my unique namespace suffix and wait for my answer. Then substitute it into deploy-test-<suffix> in every command below. Give me the oc commands to deploy the app in payment-app-java17 to OpenShift in namespace deploy-test-<suffix>. Check if the namespace deploy-test-<suffix> exists, if not create the namespace first. Build the image on the cluster (server-side) from the existing multi-stage Dockerfile in payment-app-java17. Do not build the image locally with Docker or Podman, so the steps work on any OS. Use a binary Docker-strategy build: - oc new-build --name=payment-app --strategy=docker --binary --to=payment-app:latest -n deploy-test-<suffix> - oc start-build payment-app --from-dir=payment-app-java17 --follow -n deploy-test-<suffix> Then deploy the built image and expose a route: - oc new-app payment-app -n deploy-test-<suffix> - oc create route edge payment-app --service=payment-app --port=8081 --insecure-policy=Redirect -n deploy-test-<suffix> Use an **edge (HTTPS) route**, not `oc expose svc` (which creates an HTTP-only route). Browsers silently upgrade `http://` to `https://`, and the router returns a 503 "Application is not available" for an HTTPS request to an HTTP-only host. The app listens on port **8081** (per the Dockerfile's `EXPOSE`), so the route must point at 8081. Explain each command briefly as a comment, and tell me how to get the final app URL (it will be `https://`). Create a deployment script named "deploy-to-openshift.sh" that runs all the commands in sequence. The script MUST include a preflight check, before any build steps, that verifies the cluster's internal image registry is Ready. The build pushes its output image to the internal registry, so if the registry is not up, the build fails with a misleading `InvalidOutputReference` error. The preflight check must: - Confirm at least one image registry pod in the `openshift-image-registry` namespace is `Running` and Ready (not just the `cluster-image-registry-operator` pod). Use the label selector `-l docker-registry=default` to find the registry pods — do not grep by pod name, which is brittle. - Fail fast with a clear, actionable message if the registry is not Ready, pointing the user at the storage/registry fix below — instead of letting the build fail cryptically later. - Detection only: the preflight reports the problem and the `emptyDir`/PVC fix; it MUST NOT auto-patch the cluster registry config (that is a cluster-admin action, not the script's job). The script MUST ALSO include the following (each corresponds to a gotcha documented below — implement them when generating the script, do not assume a prior script already does): - **Idempotent re-run:** before `oc new-build`, delete any existing BuildConfig AND ImageStream for the app (suppress "not found" errors), so re-running the script doesn't fail with "already exists". See *BuildConfig Already Exists* and *ImageStreamTag Already Exists*. - **Post-build tag verification:** immediately after `oc start-build`, confirm the ImageStream actually received a tag (`oc get is <app> -o jsonpath='{.status.tags[*].tag}'`). If empty, the build failed before pushing — fail fast with the build-log commands instead of letting `oc new-app` fail later with "image stream has no tags". See *PullBuilderImageFailed*. - **Service port correctness:** after `oc new-app`, ensure the Service targets the container's actual port (the Dockerfile's `EXPOSE` value, `8081` here) rather than the `oc new-app` default of `8080`; patch it if needed. See *Route returns 503 … EMPTY endpoints*. - **Edge (HTTPS) route:** create the route with `oc create route edge … --insecure-policy=Redirect`, not `oc expose svc`. See *Route returns 503 … HTTP-only route*. - **Final URL:** print the application URL as `https://` (the edge route redirects http→https). Assumptions the script may rely on (state them in a header comment): the user is already logged in to the target cluster (`oc login` done) and `oc` is on PATH. ## Common Gotchas ### InvalidOutputReference Error **Error:** `Error from server (BadRequest): build payment-app-1 failed: InvalidOutputReference: Output image could not be resolved.` This error is misleading — it points at the *output image*, but there are two distinct causes. Check them in this order. **Cause 1 (most common): the cluster's internal image registry is not Ready.** The build needs somewhere to push its output image — the internal registry in the `openshift-image-registry` namespace. If that registry isn't up, the ImageStream never gets a `status.dockerImageRepository`, so the build's output target can't be resolved. **One-glance diagnostic:** run `oc get is payment-app -n deploy-test-<suffix>` and look at the **IMAGE REPOSITORY** column. - **Empty** → the registry is the problem (this cause). Do NOT debug your BuildConfig. - **Populated** (e.g. `image-registry.openshift-image-registry.svc:5000/...`) → registry is fine; see Cause 2. **Confirm the registry state:** ```bash oc get pods -n openshift-image-registry ``` You need at least one `image-registry-*` pod at `1/1 Running` — not just `cluster-image-registry-operator`. If the `image-registry-*` pods are `0/1`, they are not Ready. **Most common root cause:** the registry has no storage backend configured, so its pod never becomes Ready. Fix for a test/workshop cluster: ```bash oc patch configs.imageregistry.operator.openshift.io/cluster --type merge \ -p '{"spec":{"managementState":"Managed","storage":{"emptyDir":{}}}}' ``` Then wait until an `image-registry-*` pod reports `1/1 Running`: ```bash oc get pods -n openshift-image-registry -w ``` ⚠️ `emptyDir` is **ephemeral** — images are lost if the registry pod restarts or reschedules. Fine for `deploy-test-*` namespaces, not for production. For persistence use a PVC instead: ```bash oc patch configs.imageregistry.operator.openshift.io/cluster --type merge \ -p '{"spec":{"managementState":"Managed","storage":{"pvc":{"claim":""}}}}' ``` (Empty `claim` auto-creates a PVC, assuming a default StorageClass exists.) The deployment script's preflight check catches this case before the build runs. **Cause 2: the `oc new-build` command was missing the `--to` flag.** If the IMAGE REPOSITORY column is populated but the build still fails, the BuildConfig may have no output target. Always include `--to=<image-name>:latest` on a binary build: ```bash oc new-build --name=payment-app --strategy=docker --binary --to=payment-app:latest -n deploy-test-<suffix> ``` The `--to` flag tells OpenShift to push the built image to an ImageStream. Without it, OpenShift doesn't know where to store the resulting container image. ### BuildConfig Already Exists Error **Error:** `error: buildconfigs.build.openshift.io "payment-app" already exists` **Cause:** A BuildConfig with the same name already exists from a previous deployment attempt. The `oc new-build` command cannot create a resource that already exists. **Solution:** Delete the existing BuildConfig before creating a new one, and also delete the ImageStream (see next gotcha). The deployment script handles this automatically by deleting both before recreating. ### ImageStreamTag Already Exists Error **Error:** `error: imagestreamtag.image.openshift.io "payment-app:latest" already exists` **Cause:** When deleting a BuildConfig, the associated ImageStream is NOT automatically deleted. When `oc new-build` runs again, it fails because the ImageStreamTag still exists. **Solution (safe for scripts):** Delete both the BuildConfig AND the ImageStream, suppressing "not found" errors: ```bash oc delete bc payment-app -n deploy-test-<suffix> 2>/dev/null || true oc delete is payment-app -n deploy-test-<suffix> 2>/dev/null || true sleep 2 oc new-build --name=payment-app --strategy=docker --binary --to=payment-app:latest -n deploy-test-<suffix> ``` ### PullBuilderImageFailed / "image stream has no tags" **Errors (two faces of the same problem):** - Build: `Failed (PullBuilderImageFailed)` ... `reading manifest ... manifest unknown` - Deploy: `oc new-app` → `error: no tags found on matching image stream` **Cause:** The build **failed before pushing an image**, so the ImageStream stayed empty. The most common reason is a **base image tag in the Dockerfile that doesn't exist** (e.g. Docker Hub removed the `openjdk`-based Maven tags, so `maven:3.9-openjdk-17-slim` returns `manifest unknown`). **Diagnose:** ```bash oc get builds -n deploy-test-<suffix> oc logs build/payment-app-1 -n deploy-test-<suffix> --tail=40 oc get is payment-app -n deploy-test-<suffix> -o jsonpath='{.status.tags[*].tag}{"\n"}' ``` **Solution:** Use a base image tag that exists, fully-qualified with `docker.io/library/`: ```dockerfile # Bad (removed from Docker Hub): # FROM maven:3.9-openjdk-17-slim AS build # Good (Eclipse Temurin replaced the OpenJDK builds): FROM docker.io/library/maven:3.9-eclipse-temurin-17 AS build ``` The deployment script verifies the ImageStream has a tag immediately after the build and fails fast if it doesn't. ### Route returns 503 "Application is not available" (HTTP-only route) **Symptom:** The pod is `1/1 Running`, the Service has endpoints, ports line up — yet the route URL shows the router's **"Application is not available"** page (503). `curl -i http://<host>/` returns **200 + HTML**, but the browser fails. **Cause:** `oc expose svc/payment-app` creates an **HTTP-only route** with no TLS. Browsers silently upgrade `http://` to `https://`; with no matching TLS route the router returns 503. **Solution:** Use an **edge-terminated (HTTPS) route** that redirects HTTP→HTTPS. Substitute `<app-port>` with the container's port (the Dockerfile's `EXPOSE` value): ```bash oc delete route <app> -n deploy-test-<suffix> oc create route edge <app> \ --service=<app> --port=<app-port> \ --insecure-policy=Redirect -n deploy-test-<suffix> oc get route <app> -n deploy-test-<suffix> -o jsonpath='https://{.spec.host}/{"\n"}' ``` **Related — 503 with EMPTY endpoints (port mismatch):** If `oc get endpoints` is *empty*, `oc new-app` defaulted the Service to a port the app isn't listening on (commonly 8080). Set it to the container's actual port: ```bash oc patch svc <app> -n deploy-test-<suffix> --type merge \ -p '{"spec":{"ports":[{"name":"<app-port>-tcp","port":<app-port>,"targetPort":<app-port>,"protocol":"TCP"}]}}' ``` > In this repo's deployment, `<app>` is `payment-app` and `<app-port>` is `8081` (from `EXPOSE 8081` in `payment-app-java17/Dockerfile`). Always confirm the port from the Dockerfile rather than assuming a default.
  2. Hand it to Bob. In the Bob chat panel, make sure you're in Code mode, then add deploy-openshift.md as context with @ → Add File and send the message. Bob will ask for your namespace suffix first, then generate the oc commands.
    💡 How to structure your spec file
    A well-structured spec file is what makes an agent work efficiently. The more your spec pins down what good output looks like, the constraints it must hold to, and the failure modes to avoid, the less the agent has to guess, and the fewer rounds of back-and-forth you need.

    A vague, few-line prompt leaves too much open: the agent fills the gaps with reasonable-but-different choices each time, so results vary and edge cases get rediscovered the hard way. A spec that states intent, lists explicit requirements, and names known gotchas up front narrows that space, so the agent converges on the same working result.

    That is why this format produces more consistent output and fewer errors: a clear, complete spec front-loads the thinking, instead of leaving the agent to improvise and you to debug.

    Curious how much it matters? Try the bare-bones version of this prompt instead, run it through Bob, and compare the two processes: how many follow-ups each takes, where each one stalls, and how close the result is to working on the first try.
2
Log in to the cluster and run the steps
First, log in to the cluster (works the same in any terminal: macOS Terminal, Windows PowerShell, or Linux shell):

oc login --token=<your-token> --server=<cluster_url>

Then run the deploy-to-openshift.sh script Bob generated. After logging in, that's the only thing you need to run: it executes all the oc commands in order, with the preflight and verification checks built in. Make it executable and run it:

chmod +x deploy-to-openshift.sh && ./deploy-to-openshift.sh

Watch the build stream from the cluster as it runs.
💡 Troubleshoot with Bob, then fold it back into the spec
If anything fails, work through it with Bob live. Share the error as context to Bob, give it pointers on what you expected to happen, and let it propose the fix. Then re-run the script and repeat, sharing each new error back, until you get a working URL for the deployed app.

Once it works, ask Bob to wrap the findings and gotchas back into your spec, a skill, or a reference guide, so the fixes you just discovered live become a durable artifact instead of staying in your terminal scrollback. Closing that loop, feeding real failures back into the spec, skill, or guide, is exactly how a rough prompt becomes a reliable one, and it means the next person benefits from your experimentation instead of rediscovering the same gotchas from scratch.

Review what Bob delivered
