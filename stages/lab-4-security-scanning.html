Lab 4 · Security
Security Scanning
Run a contextual security analysis and get a fix for every finding
Prerequisites
✅ Before You Start
  1. Lab 2 completed, so you have the payment-app-java17 project open in the Bob IDE with its test suite passing.
💬 OVERVIEW
  • Now that we know the app works correctly (tests pass), we need to know it's also safe to ship. We'll ask Bob to perform a contextual security analysis: not just pattern-matching for known bad strings, but reasoning about the code's semantics to surface logic flaws, insecure patterns, and risky handling of sensitive data.
  • Bob produces a report with a severity rating and a concrete fix recommendation for every finding, and it can apply those fixes right in the IDE.
Step-by-Step
1
Ask Bob for a contextual security analysis
As in the earlier labs, write the prompt as a Markdown file in the workspace, then hand that file to Bob. The prompt asks Bob to review the app for secrets, logic flaws, missing validation, and risky handling of sensitive data, and to produce a report with a fix for every finding.
  1. Create the prompt file. In the Explorer panel, create a New File named security-analysis.md, paste the prompt below into it, and save (⌘S / Ctrl+S).
    Prompt · Contextual Security Analysis
    ▼
    Perform a contextual security analysis of the payment-app-java17 application. Review the source and configuration for: - Hardcoded secrets, API keys, passwords, or tokens - Logic flaws and insecure patterns - Missing or weak input validation - Risky handling of sensitive data (e.g. card numbers, PII) For each issue found, show the file, line number, severity, and a one-line fix recommendation. Produce a report: SecurityScanReport.md
  2. Hand it to Bob. In the Bob chat panel, make sure you're in Code mode, then add security-analysis.md as context with @ → Add File and send the message.
2
Review the findings and suggested fixes
Open SecurityScanReport.md. Expect a mix of HIGH, MEDIUM, and LOW severity findings, each with the exact file name and line number. This is contextual analysis, not just string matching: Bob reasons about what the code actually does, so it can flag things like weak input validation or sensitive data being logged or persisted, and explain why each is a risk.

What makes this powerful isn't just that Bob found the issues; the report includes a suggested fix for every single finding. The developer doesn't have to figure out how to fix it, Bob tells them exactly what to do. And if they want to go further, they can simply ask Bob to fix the issues listed in the report, right there in the IDE.
💡 Tip
From automated tests to security analysis, Bob addressed both correctness and security: areas that normally require separate tools, teams, and later checkpoints in the SDLC.

This is what shift-left looks like in practice: issues were surfaced and resolved directly earlier on during dev time before any code even reached the CI/CD pipeline.

Keep in mind: Bob's security analysis is an extra layer, not a replacement for existing SAST, DAST, or vulnerability management tooling. Your enterprise security processes still apply; Bob catches issues earlier, before code leaves the developer's machine.

And you're not limited to Bob's own analysis: you can plug your existing security tools into Bob via MCP servers or their APIs/SDKs, then ask Bob to run them and reason over the results, bringing your established scanners right into the same conversational workflow.
