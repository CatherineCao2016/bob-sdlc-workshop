Lab 8 · Operate
Day-2 SRE Ops
Operate the running payment app on Day 2: health-check it, then scale it under load, all with Bob's help
Prerequisites
✅ Before You Start
  1. Lab 6 completed, so payment-app is deployed and running in your own deploy-test-<suffix> namespace, exposed via an edge (HTTPS) route on container port 8081.
  2. You are logged in via the oc CLI to the same cluster (oc login --token=<your-token> --server=<cluster_url>), and you know your assigned namespace suffix (for example bob-1).
  3. You have the project open in the Bob IDE, so you can write a prompt as a Markdown file and hand it to Bob, exactly as in the earlier labs.
💬 OVERVIEW
  • Shipping the app was Day 1. Day 2 is everything after: keeping it healthy, responding to load, and proving it stays available when you change it. That is the SRE half of the SDLC, and it never really ends.
  • Day-2 work usually depends on tribal knowledge: the right oc commands, the correct flags, the safe sequencing, and the checks that confirm nothing broke. With Bob, you describe the outcome you want and let it run the commands, watch the results, and report back.
  • In this lab you operate the app you deployed in Lab 6: produce a written health report, then scale the deployment out to handle load and, as a separate deliberate action, scale it back down to baseline, confirming it stays reachable the whole time. As before, you write each prompt as a Markdown file and hand it to Bob in Code mode.
Step-by-Step
1
Ask Bob for a health check and a written report
Your first Day-2 task is to find out how the deployed app is actually doing. As in the earlier labs, write the prompt as a Markdown file in the workspace, then hand that file to Bob. The prompt asks Bob to inspect the running payment-app in your namespace, check it from several angles, and write the findings into a clear health-report.md with an overall status.
  1. Create the prompt file. In the Explorer panel, create a New File named health-check.md, paste the prompt below into it, replace <suffix> with your assigned suffix (or let Bob ask you for it), and save (⌘S / Ctrl+S).
    Prompt · Health Check + Report
    ▼
    Before running anything, ask me for my namespace suffix and wait for my answer. Then use it wherever the namespace deploy-test-<suffix> is referenced. Perform a Day-2 health check on the deployed payment-app in namespace deploy-test-<suffix> and write the findings to a Markdown file named health-report.md in the workspace. The app is a stateless Spring Boot service listening on container port 8081, exposed via an edge (HTTPS) route named payment-app. Work out the right commands yourself and run them, do not invent flags. Check the app from these angles and capture what you find for each: 1. Pod status, readiness, and restarts. Flag any pod that is not Running and Ready, and report each pod's restart count. 2. Deployment rollout status, including desired vs available replicas. 3. Service endpoints: confirm there is at least one ready endpoint on port 8081. An empty endpoints list means traffic cannot reach any pod. 4. Route reachability over HTTPS: report the HTTP status code. Treat 2xx/3xx as reachable; flag anything else, especially a 503 "Application is not available". 5. Recent logs scanned for errors: summarize any ERROR, Exception, or stack-trace lines. If there are none, say so explicitly. 6. Basic resource usage, only if metrics are available. If metrics are not installed, note that and continue; do not treat it as a failure. Then write health-report.md with: - A title and timestamp. - An overall STATUS line: "healthy" or "needs attention". - One short section per check above with the key numbers and a pass/fail note. - A "Recommended follow-ups" section listing any concrete actions (or "none" if all checks pass). Keep the report concise and skimmable. Show me the final report.
  2. Hand it to Bob. In the Bob chat panel, make sure you're in Code mode, add health-check.md as context with @ → Add File, and send the message. Bob asks for your suffix, runs the checks, and writes health-report.md.
💡 Read the report, not just the exit codes
The point of a written report is that it captures a point-in-time snapshot you can compare against later. Skim the overall status and the follow-ups first. If Bob flags anything (a restarting pod, empty endpoints, a 503 on the route), work through it with Bob live before moving on, the same way you debugged the deploy in Lab 6.
2
Ask Bob to scale the deployment out under load
The second Day-2 task is a real operational change: scale out to absorb more traffic and prove the app stays available the whole time. Describe the outcome you want and let Bob choose and run the right commands. Write this prompt as a Markdown file and hand it to Bob just like the last one.
  1. Create the prompt file. Create a New File named scale-up.md, paste the prompt below, and save.
    Prompt · Scale Out
    ▼
    Before running anything, ask me for my namespace suffix and wait for my answer. Then use it wherever the namespace deploy-test-<suffix> is referenced. I want to scale the deployed payment-app in namespace deploy-test-<suffix> out to handle more load, and prove it stays available the whole time. The app is a stateless Spring Boot service on container port 8081, exposed via an edge (HTTPS) route named payment-app. Work out the right commands yourself and run them, do not invent flags. Do this step by step and report after each step: 1. Record the starting state: note the current replica count of the deployment so we know what to scale back to later. 2. Scale the deployment out to 3 replicas. 3. Wait until all 3 replicas are Running and Ready, and confirm the Service now lists 3 healthy endpoints on port 8081. 4. While scaled out, verify the route still serves traffic over HTTPS: send a handful of requests and report the HTTP status codes. They should all be successful (2xx/3xx); flag anything else, especially a 503. Summarize what changed at each step and confirm the app stayed reachable throughout. Tell me the original replica count so I can scale it back down in the next step.
  2. Hand it to Bob. In Code mode, add scale-up.md with @ → Add File and send. Bob scales out, waits for readiness, and checks the route, reporting at each step.
💡 Note
This is a simple, stateless app, so scaling it is low-risk. The operation itself gets harder for stateful or more complex apps, but the discipline you're practicing carries over directly: make a change, then prove the app stayed available before moving on. That same verify-as-you-go habit is what makes heavier Day-2 operations like rolling restarts and rollbacks safe.
3
Ask Bob to scale the deployment back down
Scaling out is only half the operation, a clean Day-2 change also means returning to the baseline once the load passes. In a second prompt, ask Bob to scale back down to the original size and confirm the app is still healthy afterwards.
  1. Create the prompt file. Create a New File named scale-down.md, paste the prompt below, and save.
    Prompt · Scale Back Down
    ▼
    Before running anything, ask me for my namespace suffix and wait for my answer. Then use it wherever the namespace deploy-test-<suffix> is referenced. Scale the deployed payment-app in namespace deploy-test-<suffix> back down to its original size (1 replica unless I tell you otherwise), and confirm it stays available. The app is a stateless Spring Boot service on container port 8081, exposed via an edge (HTTPS) route named payment-app. Work out the right commands yourself and run them, do not invent flags. Do this step by step and report after each step: 1. Scale the deployment back down to its original replica count. 2. Wait until the rollout settles, then confirm only the expected number of pods are Running and Ready and the Service lists a single healthy endpoint on port 8081. 3. Verify the route still returns a healthy HTTP status code over HTTPS. Summarize what changed and confirm the deployment is back to its original size and the app stayed reachable throughout.
  2. Hand it to Bob. In Code mode, add scale-down.md with @ → Add File and send. Bob scales back in, waits for the rollout to settle, and confirms the route is still healthy.
💡 Note
The skill here isn't the operation itself, it's driving operations through Bob: describe the outcome you want in plain language, and let it run the commands and verify the result. That same agent-driven workflow scales to any Day-2 task.
Lab Summary
🏆 WHAT YOU ACHIEVED
  • You operated the deployed payment app on Day 2, driving live cluster operations by handing Bob a prompt instead of memorizing oc commands.
  • You produced a written health report (health-report.md) covering pod status and restarts, rollout status, Service endpoints, HTTPS route reachability, recent error logs, and resource usage, with a clear healthy / needs-attention verdict.
  • You performed a real scaling operation: scaled payment-app out to 3 replicas, confirmed all replicas became Ready and the Service had 3 endpoints, verified the route kept serving traffic, then scaled back down.
  • In both tasks you validated as you went, confirming the app stayed available throughout, the way Bob watches each result and reports anomalies rather than just firing commands.
  • The takeaway: Bob turns Day-2 operations into plain-language requests, so you drive the cluster by describing the outcome you want instead of memorizing commands. The same approach extends to other Day-2 work like rolling restarts, rollbacks, and auto-healing.
