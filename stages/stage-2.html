Lab 02 · Tests
Generate Tests
Generate a full test suite covering happy paths, edge cases, and failure scenarios
Prerequisites
✅ Before You Start
  1. Lab 1a completed, so you have the modernized payment-app-java17 project open in the Bob IDE. The tests in this lab target that directory. If you skipped Lab 1a, you can grab the ready-made Java 17 version here: payment-app-java17.
💬 OVERVIEW
  • Testing is a core part of any software delivery lifecycle; industry standards like CI/CD, DevSecOps, and agile all mandate that code is validated before it ships. We'll ask Bob to generate a full test suite covering happy paths, edge cases, and failure scenarios, with no manual test writing required.
Step-by-Step
1
Ask Bob to generate the test suite
As in the earlier labs, write the prompt as a Markdown file in the workspace, then hand that file to Bob. It asks for JUnit 5 integration tests covering the full payment lifecycle (authorization, capture, refund) plus the failure scenarios, and a coverage report at the end.
  1. Create the prompt file. In the Explorer panel, create a New File named generate-tests.md, paste the prompt below into it, and save (⌘S / Ctrl+S).
    Prompt · Generate Tests
    ▼
    Generate JUnit 5 integration tests for the payment API. Cover: successful authorization, declined card, capture after auth, refund after capture, invalid card number, duplicate refund attempt. Use MockMvc. Assert HTTP status codes and response body fields. Target 80% code coverage. Use Java 17. Generate tests for the payment-app-java17 directory. Configure JaCoCo in the pom.xml to measure coverage, then summarize the JaCoCo results in a report named PaymentApiIntegrationTestCoverageReport.md.
  2. Hand it to Bob. In the Bob chat panel, make sure you're in Code mode, then add generate-tests.md as context with @ → Add File and send the message.
💡 Tip
JaCoCo (Java Code Coverage) is a library that measures how much of your code is exercised by tests; it generates the coverage percentage report. MockMvc is a Spring testing framework that lets you simulate HTTP requests to your REST endpoints without starting a real server, making tests fast and isolated.
2
Watch Bob work through the task
Before writing any code, Bob will first read the existing source files to gather context; it needs to understand the controllers, models, and endpoints before it can write meaningful tests.

Once it has enough context, Bob will create a to-do list and work through each item: files are created one by one and checked off as complete.
3
Review the coverage report
Open PaymentApiIntegrationTestCoverageReport.md and review the summary: pass/fail counts, coverage percentage, and any flagged edge cases. This is the kind of output a developer would normally spend hours producing manually.
💡 Tip
You should expect all tests to pass ✅.
Lab Summary
🏆 WHAT YOU ACHIEVED
  • Bob generated a full JUnit 5 integration test suite for the payment API: happy paths, edge cases, and failure scenarios, with no manual test writing.
  • You watched Bob's workflow: it read the source files first to understand controllers, models, and endpoints, then worked through a to-do list item by item.
  • The tests use MockMvc to simulate HTTP requests and assert status codes and response bodies, with JaCoCo measuring coverage against the 80% target.
  • You reviewed PaymentApiIntegrationTestCoverageReport.md: pass/fail counts, coverage percentage, and flagged edge cases.
  • The takeaway: validation is built into the workflow; the code is proven correct before it moves further down the pipeline.
