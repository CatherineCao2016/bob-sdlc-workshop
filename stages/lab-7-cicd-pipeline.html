Lab 7 · Pipeline
CI/CD Pipeline
Automate the manual deploy from Lab 6: CI on every commit, auto-deploy to staging, manual approval to promote to production
Prerequisites
✅ Before You Start
  1. Open the payment-app-java17 folder as the project in Bob. For this lab that folder is the git repository root, so the workflow lives at its root (.github/workflows/ci-cd.yml) and build paths are repo-relative. Its origin remote should point at a GitHub repository you can push to (a fork is fine). Have your assigned namespace suffix ready (for example bob-n). Don't have a working Java 17 app from an earlier lab? Get the starter here: payment-app-java17 starter.
  2. The gh CLI installed and authenticated (gh auth login), with permission to set Actions secrets, variables, and environments on that repo. Need it? See Install the GitHub CLI.
  3. The oc CLI logged in (oc login --token=<your-token> --server=<cluster_url>) so the launch script can read your cluster URL and token. No Docker or Java needed; the image builds on the cluster. Need oc? See Install the oc CLI.
💬 OVERVIEW
  • Lab 6 deploys the app to OpenShift by hand to validate the path; this lab automates that flow. We use GitHub Actions here, but Bob can generate the equivalent for Jenkins, GitLab CI, Azure DevOps, or Tekton; the concepts carry over regardless of the tool.
  • The pipeline follows industry-standard practice: CI runs automatically on every commit (build, test, scan). CD auto-promotes to staging so you can validate the live app. Only when someone explicitly approves does it touch production. That human approval gate is the balance between developer speed and operational control, and in regulated industries it is often a compliance requirement.
  • Staging and production are two namespaces that are yours alone on the shared cluster: deploy-test-<suffix> (staging) and deploy-prod-<suffix> (production), both created by the pipeline if they don't already exist. The image is built once on the cluster, validated in staging, then promoted to production as the exact same artifact, never rebuilt.
  • You generate the workflow, then ask Bob to configure the GitHub repo and hand you a single launch-pipeline.sh script. Running it sets the repo's secrets and variable, creates the production approval gate, and pushes the must-have files, all in one go. Then you watch the run live, CI, the staging deploy, and the production approval gate, and approve it to promote.

1
Ask Bob to generate the CI/CD workflow
As in the earlier labs, write the prompt as a Markdown file in the workspace, then hand that file to Bob. It describes the full pipeline: CI on every commit, an automatic deploy to staging, and a manual-approval gate before production, all built with an on-cluster oc build. Everything lands in a single workflow file, .github/workflows/ci-cd.yml.
  1. Create the prompt file. In the Explorer panel, create a New File named cicd-pipeline.md, paste the prompt below into it, and save (⌘S / Ctrl+S).

Variables are available in all workflow contexts including environment.url; secrets are not. Never hardcode credentials. The only secrets are OPENSHIFT_SERVER and OPENSHIFT_TOKEN — do not introduce any other secret (such as a cluster apps domain). Set each environment's url from the route the job retrieves at runtime (a step output via oc get route), not from a separate domain secret. IMPORTANT: derive the namespace names from the NAMESPACE_SUFFIX variable in the workflow itself — for example deploy-test-${{ vars.NAMESPACE_SUFFIX }} and deploy-prod-${{ vars.NAMESPACE_SUFFIX }}. Do NOT bake my literal suffix into the file; asking me for the suffix is only so you understand the naming, the committed workflow must read it from the variable so a different suffix just works. CI (runs on every PR and push to main): 1. Checkout, set up JDK 17, build with Maven from the repository root 2. Run JUnit tests; skip if the commit message contains [skip checks] 3. Run OWASP dependency-check (fail on CVSS >= 7); skip if [skip checks] 4. Run Semgrep SAST scan; skip if [skip checks] IMPORTANT: the skippable quality-gate jobs (test, owasp, semgrep) must NOT be in the 'needs' array of the build or deploy jobs. Only the Maven build job should be a dependency. A skipped job listed in 'needs' makes all downstream jobs skip regardless of their own 'if' conditions. Build on the cluster + push to staging (on push to main, after CI): 5. oc login (as above), create deploy-test-<suffix> if it does not exist, then build the image on the cluster from the repo and tag it with the git SHA: - delete any existing BuildConfig AND ImageStream for payment-app first (suppress not-found), so re-runs do not fail with "already exists" - oc new-build --name=payment-app --strategy=docker --binary --to=payment-app:${GITHUB_SHA} -n deploy-test-<suffix> (create if missing) - oc start-build payment-app --from-dir=. --follow -n deploy-test-<suffix> - verify the ImageStream actually received the ${GITHUB_SHA} tag; if empty, fail fast and print the build logs (the build failed before pushing) CD Staging (automatic, after the build): 6. Deploy the freshly built image to deploy-test-<suffix>: oc new-app on first run, otherwise update the deployment's image to payment-app:${GITHUB_SHA} 7. Ensure the Service targets port 8081 (not the oc new-app default of 8080); patch it if needed, or the route returns 503 with empty endpoints 8. Ensure an edge (HTTPS) route named payment-app exists: oc create route edge payment-app --service=payment-app --port=8081 --insecure-policy=Redirect -n deploy-test-<suffix> (create if missing) 9. Wait for rollout, then explicitly wait for pod readiness: oc wait --for=condition=ready pod -l deployment=payment-app -n deploy-test-<suffix> --timeout=2m 10. Add a short grace period for route propagation, then read the route URL: oc get route payment-app -n deploy-test-<suffix> -o jsonpath='https://{.spec.host}' 11. Run a smoke test against the https route: GET the Spring Boot Actuator health endpoint at /actuator/health and require HTTP 200 (the body reports {"status":"UP"}). Do not invent a business endpoint or payload; the app's real APIs live under /api/payments, but health is the reliable readiness check, so use /actuator/health for the smoke test. CD Production (runs only after MANUAL approval): 12. Gate this job behind a GitHub Environment named "production" with a required reviewer, so it pauses for human approval before anything runs. 13. Create deploy-prod-<suffix> if it does not exist. 14. Promote the EXACT image validated in staging — never rebuild. Use oc tag to copy the image across namespaces on the same cluster: oc tag deploy-test-<suffix>/payment-app:${GITHUB_SHA} deploy-prod-<suffix>/payment-app:${GITHUB_SHA} 15. Deploy the promoted image to deploy-prod-<suffix> with a rolling update (maxUnavailable: 1), Service on 8081, and an edge (HTTPS) route named payment-app 16. Wait for readiness and confirm the prod route serves traffic the same way: GET /actuator/health and require HTTP 200. Print the production https URL. Same OPENSHIFT_SERVER and OPENSHIFT_TOKEN are used for both namespaces. All in a single workflow file: .github/workflows/ci-cd.yml Just generate the workflow file for now; a later step configures the repo and launches it. ## Common Gotchas (build in defenses for these) - Internal registry must be Ready before any build, or the build fails with a misleading InvalidOutputReference. Add a preflight check and fail fast with a clear message if the registry is not Ready or a build cannot push. - Idempotent builds: delete the BuildConfig AND the ImageStream before oc new-build (suppress not-found), or re-runs fail with "already exists". - Service port must be 8081 (the Dockerfile's EXPOSE), not the oc new-app default of 8080. - Use an edge route with --insecure-policy=Redirect, not oc expose svc; HTTP-only routes return 503 in browsers. - Production promotes the same ${GITHUB_SHA} image via oc tag; it must never rebuild.

    💡 How to structure your spec file
    The more your spec pins down what good output looks like, the constraints it must hold to, and the failure modes to avoid, the less the agent has to guess. The gotchas section above is doing real work: it names the issues that commonly bite an on-cluster build (registry readiness, idempotent builds, the 8081 port, the edge route), so the pipeline gets them right the first time instead of rediscovering them in CI.
2
Walk through the pipeline structure
Open .github/workflows/ci-cd.yml and notice the three distinct stages: CI (build, test, scan), CD Staging (on-cluster build, deploy to deploy-test-<suffix>, smoke test), and CD Production (manual approval, then oc tag promotion into deploy-prod-<suffix> and a rolling deploy).

Pay attention to the promotion pattern: production never rebuilds the image. It promotes the exact same artifact that passed staging, identified by the git SHA, with oc tag moving it from your staging namespace to your prod namespace on the same cluster. Same SHA, same bits. This is the industry standard and eliminates an entire class of "works in staging, breaks in prod" bugs, because what you tested is byte-for-byte what you ship.
3
Configure the repo and launch the pipeline
Rather than click through GitHub's settings by hand, ask Bob to wire everything up and hand you a single script that pushes the files and triggers the run. Send the prompt below in Code mode; Bob uses the gh and oc CLIs you're already logged in to.
Prompt · Configure + launch script
▼
I want to actually run this pipeline. First, ask me for (1) my namespace suffix and (2) the target GitHub repository as owner/name, and wait for my answers. Assume only that the gh CLI is installed and I'm authenticated (gh auth login done) and oc is logged in to the cluster. Do NOT assume this folder is already a git repository or that an 'origin' remote exists; the script must set that up. Generate one idempotent script named launch-pipeline.sh that, when I run it: 1. Reads my OpenShift server and token from oc (oc whoami --show-server and oc whoami -t) and sets them as the GitHub repo secrets OPENSHIFT_SERVER and OPENSHIFT_TOKEN using `gh secret set`. 2. Sets the GitHub repo variable NAMESPACE_SUFFIX to my suffix using `gh variable set`. 3. Creates (or updates) a GitHub Environment named "production" with me as a required reviewer, so the production job pauses for approval. Get my numeric user id with `gh api user --jq .id`, then PUT repos/<owner>/<repo>/environments/production with a JSON body whose "reviewers" is an ARRAY, piped via `gh api --method PUT ... --input -` with a here-doc like {"reviewers":[{"type":"User","id":<my-id>}]}. Do NOT build the reviewers field with repeated `-F reviewers[]=...` flags — gh turns those into an object, not an array, and GitHub rejects it with HTTP 422. 4. Prepares the git repository: if this folder is not already a git repo, run `git init` and `git branch -M main`; run `gh auth setup-git` so git can push over HTTPS using my gh login; and ensure an 'origin' remote points at https://github.com/<owner>/<repo>.git (add it if missing, update it if it points elsewhere). 5. Stages, commits, and pushes every file the pipeline needs to origin main to trigger the run: the .github/workflows/ci-cd.yml workflow plus the application sources, Dockerfile, and pom.xml at the repo root, and any file the workflow's own steps reference (for example an owasp-suppressions.xml if the OWASP job points at one) when it exists. Use a commit message that contains [skip checks] by default. Handle "nothing to commit" gracefully (don't fail if there are no changes). 6. Prints the Actions run URL and then streams the run with `gh run watch` so I can follow CI, the staging deploy, and the production approval gate. Requirements: - Idempotent and re-runnable: update existing secrets / variable / environment / remote instead of erroring, and don't fail if there is nothing new to commit. - Never print or commit my token; pass it to gh via stdin or a shell variable, never as a literal written into the repo. - Add a header comment listing the assumptions (gh authenticated, oc logged in) and echo each step so I can follow along. - Do not run any oc build or deploy yourself; the GitHub Actions workflow does all the cluster work.
The script reads your existing GitHub and cluster sessions, so sign in to both first (you enter your own credentials; the script never sees them):
Terminal · Sign in to GitHub and the cluster
▼
# authenticate the GitHub CLI (opens a browser to sign in) gh auth login # log in to the OpenShift cluster (get the token and server from your instructor # or the console's "Copy login command") oc login --token=<your-token> --server=<cluster_url>
Then, when Bob has written launch-pipeline.sh, review it and run it from the project root:
Terminal · Push the files and trigger the run
▼
chmod +x launch-pipeline.sh && ./launch-pipeline.sh
💡 Tip
You sign in to GitHub and the cluster yourself with gh auth login and oc login; the script only reads those existing sessions, it never stores your token in the repo. The OpenShift token is short-lived, so if a later run fails to authenticate, just re-run the script to refresh the OPENSHIFT_TOKEN secret.

The script commits with [skip checks] in the message by default. The workflow bypasses the JUnit, OWASP, and Semgrep quality gates whenever the commit message contains [skip checks], which keeps a workshop run fast (those gates can take several minutes). To run the full gates instead, commit again without [skip checks] in the message.
4
Observe the run and approve production
The push triggers the workflow immediately. Follow it in the terminal where gh run watch is streaming, or open the repo's Actions tab. You'll see CI run, the staging deploy land in deploy-test-<suffix> and pass its smoke test, and then the production job stop at Waiting on its approval gate.

Approve it from the Actions run page (Review deployments → production → Approve and deploy). The production job then promotes the exact staging image with oc tag into deploy-prod-<suffix> and rolls it out. When the run is green, its logs print your production https:// URL; open it to confirm the promoted app is live.
💡 Tip
Remember the skipped gates would normally block a deploy on a failing test or a critical CVE, so a real promotion should run them. If a run fails, work the error with Bob live and fold the fix back into cicd-pipeline.md (or the launch script) so the next run already has it. No repo or cluster handy?
