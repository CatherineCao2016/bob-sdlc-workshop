Lab 01a · Modernize
Java Modernization
Upgrade the app from Java 11 to Java 17 with Bob's modernization capability
Prerequisites
✅ Before You Start
  1. Lab 1 completed, so you have the payment-app-java11 project open in the Bob IDE.
  2. A JDK (17 or later) on your PATH. The modernized app will not compile on an older JDK. Verify with java -version.
💬 OVERVIEW
  • We built the app on Java 11 intentionally. This lets us showcase one of Bob's most compelling enterprise use cases: code modernization.
  • Many organizations are running legacy Java versions across hundreds of services. Bob can analyze the codebase, identify what needs to change, and produce a structured upgrade plan before touching a single line of code.
  • The workflow has two phases: plan first, then execute. You review the plan in between, exactly how you would want an engineer to approach a risky migration.
Step-by-Step
1
Ask Bob for a modernization plan
As in Lab 1, we'll write the prompt as a Markdown file in the workspace, then hand that file to Bob. The prompt asks Bob to analyze the app and produce a plan only, with no code changes yet. Planning before changing is the same habit you saw in Lab 1: put the expectations on paper, then let Bob work against them.
  1. Create the prompt file. In the Explorer panel, hover your workspace folder and click New File, name it modernization-prompt.md, paste the prompt below into it, and save (⌘S / Ctrl+S).
    Prompt · Java Modernization Action Plan
    ▼
    Analyze the payment application and create a detailed action plan to modernize it from Java 11 to Java 17. The plan should include: 1. Summary of changes required (dependencies, APIs, syntax, config) 2. List of deprecated or removed APIs that need replacing 3. New Java 17 features that can improve the codebase (records, sealed classes, text blocks, pattern matching) 4. Updated pom.xml changes required (Java version, Spring Boot compatibility) 5. Estimated effort and risk for each change 6. Recommended order of changes to minimize risk Do not make any code changes yet. Produce the plan as: JavaModernizationPlan.md
  2. Hand it to Bob. In the Bob chat panel, make sure you're in Plan mode, then add modernization-prompt.md as context by typing @ in the chat box. A menu pops up: select Add File, then select modernization-prompt.md, and send the message.
💡 Tip
Keeping prompts as files in the workspace has another benefit: they can be reviewed, modified, and version controlled the same way as code, so your team can share and refine them over time.
2
Review the plan
Bob produces a structured JavaModernizationPlan.md. Open it and review the breakdown: what changes are required, which deprecated APIs need replacing, what new Java 17 features can be adopted (records, text blocks, pattern matching), the pom.xml updates, and the estimated effort, risk, and recommended order for each change. This is the kind of analysis that would normally take a senior developer days to produce manually.
3
Execute the modernization
As before, create a prompt file to ask Bob to execute the plan, then hand it over. Watch it work through the codebase systematically: updating dependencies, replacing deprecated APIs, and adopting Java 17 features. The prompt tells Bob to write the result to a new payment-app-java17 folder and leave the original untouched, so you can compare the two side by side.
  1. Create the prompt file. In the Explorer panel, create a New File named execute-modernization.md, paste the prompt below into it, and save (⌘S / Ctrl+S).
    Prompt · Execute the Modernization
    ▼
    Execute the JavaModernizationPlan.md: modernize the payment application from Java 11 to Java 17. Apply all changes identified in the plan: 1. Update pom.xml: Java version to 17, Spring Boot and dependency versions 2. Replace any deprecated or removed APIs with Java 17 equivalents 3. Apply Java 17 features where they improve the code: - Records for immutable model classes - Text blocks for multi-line strings - Pattern matching for instanceof checks - Sealed classes where appropriate 4. Remove Lombok if present; replace with Java records or explicit methods 5. Verify the application still compiles and runs with: mvn spring-boot:run Output the modernized application in a new folder alongside the original: ``` payment-app-java11/ ← original Java 11 (do not modify) payment-app-java17/ ← modernized Java 17 ├── src/ │ └── main/ │ ├── java/com/demo/payment/ │ │ ├── controller/ │ │ ├── service/ │ │ ├── model/ ← records replace verbose POJOs │ │ └── config/ │ └── resources/ │ ├── static/ │ └── application.properties ├── pom.xml ← updated to Java 17 + Spring Boot 3.x ├── Dockerfile └── README.md ``` Do not run the application. I will verify it myself.
  2. Hand it to Bob. In the chat panel, make sure you're in Code mode, then add execute-modernization.md as context with @ → Add File and send the message.
4
Review what Bob delivered
When Bob wraps up, it summarizes the changes it made. The original payment-app-java11 is untouched and the modernized version sits in payment-app-java17, so you can open the same file in both folders and see exactly what changed. Open these three pairs side by side:
  1. A model class becomes a record. Open model/PaymentRequest.java in both folders. The Java 11 version is a 61-line class: private fields plus a getter and setter for every one. The Java 17 version is a 26-line record that keeps the same validation annotations but drops all the boilerplate. That's roughly 60% less code for the same behavior, and Bob applied the same change to PaymentResponse.java (88 lines down to 36).
  2. The Jakarta EE namespace migration. In the same files, notice the imports flipped from javax.validation.* to jakarta.validation.*. This is the breaking change that blocks most manual Spring Boot 2 → 3 upgrades; Bob found and updated every occurrence across the codebase.
  3. The build file. Open pom.xml in both. Bob bumped <java.version> from 11 to 17 and the Spring Boot parent from 2.7.18 to 3.2.5, the coordinated jump that pulls in the Jakarta namespace above.
💡 Tip
That is one service modernized, reviewed, and explained in minutes. The same plan-then-execute workflow runs unchanged across 200 services, which is where the real enterprise value shows up.
5
Run the modernized app
First, stop the original app if it's still running: press Ctrl+C in its terminal. Otherwise you'll get a port conflict on localhost:8080. Then run:

cd payment-app-java17 && mvn spring-boot:run

Open localhost:8080 and confirm the payment flow still works exactly as it did in Lab 1: same UI, same transactions, now on Java 17.
💡 Tip
If you hit compile or runtime errors, you don't need to copy and paste them. Type @ in the chat box and select Terminal to point Bob at the terminal: it automatically pulls in the error output, diagnoses the cause, and fixes it.
Lab Summary
🏆 WHAT YOU ACHIEVED
  • Bob analyzed a legacy Java 11 codebase and produced a structured modernization plan: required changes, deprecated APIs, effort and risk per change, and a recommended order. No code was touched until you reviewed it.
  • Bob then executed the plan: upgraded pom.xml to Java 17 and Spring Boot 3.x, replaced deprecated APIs, and adopted records, text blocks, and pattern matching.
  • The original app stayed intact; the modernized version landed in its own folder for side-by-side comparison.
  • You ran the Java 17 app and confirmed the behavior is unchanged.
  • The takeaway: plan-then-execute modernization in minutes, with a workflow that scales from one service to hundreds.
