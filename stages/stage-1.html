Lab 01 · Build
Bob Builds the App
One prompt → full deployable payment app
Prerequisites
✅ Before You Start
  1. An IBMid. If you don't have one, sign up for a free trial at bob.ibm.com/trial.
  2. The Bob IDE downloaded and installed. Get it at bob.ibm.com/download.
  3. A JDK (17 or later) and Maven 3.6+ installed and on your PATH. Verify with java -version and mvn -version. You do not need to install Spring Boot; Maven downloads it automatically on first build.
💬 OVERVIEW
  • IBM Bob is an AI agent for the full software development lifecycle. It can plan, build, test, secure, and deploy applications from natural-language prompts.
  • The Bob IDE is what you will work with in this lab: a fork of VS Code, fully customized for the agentic coding experience, so everything you already know about VS Code still applies, with Bob built in as a chat-driven coding agent.
  • We're building a mock credit card payment app: backend, frontend, all in one prompt.
  • Notice how detailed the spec is: endpoints, card numbers, response codes, UI states. This is specs-driven development: putting the important technical details on paper upfront so Bob has everything it needs to deliver exactly what's expected. No back-and-forth, no misaligned deliverables.
📝 Notes
In this lab we build the app in Java 11, so we can reuse the same app for the Java modernization lab. If you'd rather skip that, you can ask Bob directly for Java 17 (or any other version). You can also find the finished app here: Java 17 version · Java 11 version.
Step-by-Step
1
Set up the project and build prompt
Bob is built on VS Code, so the editor works exactly the same way. We'll create a project, write the build prompt as a Markdown file inside it, then hand that file to Bob.
  1. Create a project. Open Bob and choose File → Open Folder… (or Open… from the Welcome screen). Pick an empty folder for your app, or create a new one first. This folder is your workspace.
  2. Sign in. Open the Bob chat panel and sign in with your IBMid (first time only).
  3. Add the build prompt as a file. In the Explorer panel, hover your folder and click New File, name it build-prompt.md, paste the prompt below into it, and save (⌘S / Ctrl+S).
    Build prompt: paste this into build-prompt.md:
    Build Prompt
    ▼
    Build a mock credit card payment processing application with: Backend (Java 11, Spring Boot): - REST API endpoints: - POST /api/payments/authorize (authorize a card transaction) - POST /api/payments/capture (capture an authorized transaction) - POST /api/payments/refund (refund a captured transaction) - GET /api/payments/{id} (get transaction status) - GET /api/payments/history (list recent transactions) - POST /admin/cache/clear (clear local cache) - GET /actuator/health (readiness probe) - GET /actuator/prometheus (metrics endpoint) - Use in-memory H2 database (no external DB needed) - Local Caffeine cache for transaction lookups - Simulate realistic processing delays (200-500ms) - Simulate random declines (10% of transactions) - Return realistic response codes (approved, declined, insufficient funds, expired card) - Use the test card numbers: - Visa: 4263970000005262 - MasterCard: 5425230000004415 - Amex: 374101000000608 Frontend (React): - Payment form: card number, expiry, CVV, amount - Transaction history dashboard showing recent payments - Status badges: Authorized (yellow), Captured (green), Declined (red), Refunded (gray) - Simple and clean. This is for a demo, not production Make it run with a single command: mvn spring-boot:run Do not run the application. I will run it myself. Also generate: - Dockerfile: multi-stage build, distroless base, non-root user - k8s/deployment.yaml: OpenShift deployment manifest with placeholder values: - Image: image-registry.openshift-image-registry.svc:5000/${NAMESPACE}/payment-app:${IMAGE_TAG} # in-cluster pull path. At deploy time: ${NAMESPACE} → bob-demo-staging (or bob-demo-prod), # ${IMAGE_TAG} → git SHA. The CI job pushes the same image via the external route ($OPENSHIFT_REGISTRY). - Namespace: ${NAMESPACE} # bob-demo-staging | bob-demo-prod - 3 replicas, resource limits, readiness/liveness probes - PodDisruptionBudget (max 1 unavailable) - Service and Route Use placeholder values only; real cluster values will be injected at deploy time. Use the following folder structure: ``` payment-app-java11/ ├── src/ │ └── main/ │ ├── java/com/demo/payment/ │ │ ├── controller/ │ │ ├── service/ │ │ ├── model/ │ │ └── config/ │ └── resources/ │ ├── static/ ← React frontend │ └── application.properties ├── pom.xml ├── Dockerfile ├── k8s/ │ └── deployment.yaml ← OpenShift manifest with placeholder values └── README.md ```
  4. Hand it to Bob. In the Bob chat panel, make sure you're in Code mode, then add build-prompt.md as context by typing @ in the chat box. A menu pops up: select Add File, then select build-prompt.md, and send the message. The spec already tells Bob what to build, so it gets to work right away.
    💡 Feature Spotlight · Context Mentions
    The @ symbol triggers context mentions, a quick way to point Bob at specific parts of your project (files, folders, terminal, and more) so it has exactly the context it needs. See the context mentions docs for everything you can reference.
    💡 Feature Spotlight · Modes
    Bob works in modes, personas tuned for different kinds of work. The built-in modes are Code (writing and modifying code), Ask (explanations and code analysis without making changes), Plan (architecture and technical plans before implementation), Advanced (full tool access for complex workflows), and Orchestrator (coordinating multi-step projects across modes). We use Code mode here since we want Bob to build. You can switch modes from the dropdown in the chat panel; see the modes docs for details. You can also create your own custom modes tailored to your team's workflows.
2
Review Bob's build plan and let it build the app
Before writing any code, Bob produces a detailed to-do list, the full build plan: project structure, data models, API controllers, service layer, database and cache, frontend, Dockerfile, and Kubernetes manifests. Depending on your allowed actions settings, Bob may pause and ask for approval before creating files or running commands, so you stay in control the whole time.

Approve the steps and let Bob work through the plan.
3
Review what Bob delivered
When it finishes, Bob writes a README.md describing everything it implemented and gives you a clear handoff message with what to do next. Notice Bob didn't only build the app; it also generated the Dockerfile and the OpenShift deployment manifest in k8s/deployment.yaml. One prompt, and you have everything needed to containerize and deploy.
4
Run the application
In a terminal, run:

cd payment-app-java11 && mvn spring-boot:run

Maven compiles the project, then starts the Spring Boot application with its embedded Tomcat server, wiring up the H2 database, cache, and REST controllers. When you see "Started PaymentApplication", the app is live on localhost:8080.
💡 Tip
If the app fails to start, Spring Boot prints a clear error explaining what went wrong, and you can hand that error to Bob to fix it.
5
Try it in the browser
Open localhost:8080 and fill in the payment form:

• Card Number: use a test card, e.g. Visa 4263970000005262
• Expiry: any future date, e.g. 12/26
• CVV: any 3-digit number, e.g. 123
• Amount: any value, e.g. 99.99

Hit Authorize and watch the transaction appear in the history dashboard. The outcome will be one of Authorized (yellow), Captured (green), Declined (red), or Refunded (gray), with a ~10% chance of a decline to simulate real-world behavior. This confirms the UI is talking to the backend: Bob generated a working application, not just code.
Lab Summary

  • You gave Bob a single detailed spec prompt and watched it plan the work before writing a line of code, with you approving each step along the way.
  • Bob built a complete payment application: Spring Boot REST backend, H2 database, cache, and a working frontend with a transaction dashboard.
  • Bob also delivered everything around the code: a README, a Dockerfile, and an OpenShift deployment manifest, so the app is ready to containerize and deploy in later labs.
  • You ran the app locally with Maven and verified it end-to-end in the browser: authorizing test payments and seeing transactions flow through Authorized, Captured, Declined, and Refunded states.
  • The takeaway: one well-written prompt produced a working, deployable application, not just code. The rest of the workshop builds on this app: testing, security scanning, infrastructure, deployment, and operations.
