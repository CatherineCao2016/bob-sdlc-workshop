Lab 04 · Deploy
Deploy to OpenShift
Manual deploy to validate the cluster before automating with CI/CD
Prerequisites
✅ Before You Start
  1. Lab 3 completed, so you have the payment-app-java17 project (with its infra/ files) open in the Bob IDE.
  2. Access to a live OpenShift cluster: any Red Hat OpenShift environment you have access to (a managed cluster, a self-provisioned one, or a sandbox). One cluster is typically shared across all attendees; because each app builds on your own laptop and only the running pod lands on the cluster, a cluster with 3 worker nodes (12 vCPU and 48 GB RAM total) comfortably supports a roomful.
  3. Your own namespace. On a shared cluster, everyone deploying into the same namespace would overwrite each other. Pick a unique suffix (for example your initials) and use deploy-test-<suffix> consistently throughout this lab.
  4. The oc CLI installed, plus a login token for your cluster. This is the only local tool you need: no Docker, Podman, or Java required, since the image builds on the cluster. The oc CLI runs the same on macOS, Windows, and Linux.
📝 Instructor Note
For a shared cluster, before the session give each attendee their own account with edit rights scoped to their namespace rather than a shared cluster-admin token. Because the image is built on the cluster (not pushed from laptops), you do not need to expose the internal registry route.
💬 OVERVIEW
  • Before we automate anything, we deploy manually first. This is intentional: it lets us validate the cluster setup, catch security context issues, and confirm the app actually runs before a pipeline ever touches it.
  • We build the image on the cluster, not on your laptop. OpenShift builds it server-side from the existing Dockerfile, so the workflow is identical whether you're on an Intel Mac, an Apple Silicon Mac, Windows, or Linux. No Docker, Podman, or local Java needed: just the oc CLI.
  • Bob generates the deployment steps. We run them, watch what happens, and fix any issues together, live, with Bob's help. This is where real-world problems get solved.
Step-by-Step
1
Ask Bob to generate the deployment steps
In the Bob chat panel, send the prompt below. It asks Bob for the oc commands to build the image on the cluster from the existing multi-stage Dockerfile and deploy the app into your own namespace. Because the build runs server-side, the same commands work on any operating system. Replace <suffix> with your unique suffix before sending.
Prompt · Generate Deployment Steps
▼
Before giving me any commands, ask me for my unique namespace suffix and wait for my answer. Then substitute it into deploy-test- in every command below. Give me the oc commands to deploy the app in payment-app-java17 to OpenShift in namespace deploy-test-. Build the image on the cluster (server-side) from the existing multi-stage Dockerfile in payment-app-java17. Do not build the image locally with Docker or Podman, so the steps work on any OS. Use a binary Docker-strategy build: - oc new-build --name=payment-app --strategy=docker --binary -n deploy-test- - oc start-build payment-app --from-dir=payment-app-java17 --follow -n deploy-test- Then deploy the built image and expose a route: - oc new-app payment-app -n deploy-test- - oc expose svc/payment-app -n deploy-test- Explain each command briefly as a comment, and tell me how to get the final app URL.
2
Log in to the cluster and run the steps
First, log in to the cluster (works the same in any terminal: macOS Terminal, Windows PowerShell, or Linux shell):

oc login --token=<your-token> --server=<cluster_url>

Then run the oc commands Bob gave you, in order. Since they're plain oc commands, there's no script to make executable and nothing OS-specific. Watch the build stream from the cluster as it runs.

If anything fails, work through it with Bob live; that's the point of this lab.
💡 Tip
If you see error: deployment "payment-app" exceeded its progress deadline, ask Bob to refer to troubleshooting-guide.md (link TBD). In the guide, we already provide what commands to run in terms of how to troubleshoot in this case, e.g.:

oc get pods -n deploy-test-<suffix> -l app=payment-app
oc describe pods -n deploy-test-<suffix> -l app=payment-app
oc describe deployment payment-app -n deploy-test-<suffix>
oc logs -n deploy-test-<suffix> -l app=payment-app --tail=100
oc get route payment-app -n deploy-test-<suffix> (get app URL once deployment succeeds)
3
Review what Bob delivered
Once the commands complete, you have:
→payment-app image built on the cluster and stored in your namespace's image stream
→payment-app running in your deploy-test-<suffix> namespace, with a route
Get the app URL with oc get route payment-app -n deploy-test-<suffix>, open it in a browser, and confirm the payment app is up and serving traffic from the cluster.
Lab Summary
🏆 WHAT YOU ACHIEVED

  • You logged in to the cluster and ran the steps, deploying the payment app to OpenShift for the first time, with the image built on the cluster so the workflow worked identically on any laptop.
  • Any failures were debugged live with Bob's help, validating the cluster setup and catching issues before automation.
  • You confirmed the app is running in your deploy-test-<suffix> namespace via its route, isolated from other attendees on the shared cluster.
  • The takeaway: deploy manually first to validate the path; Lab 4b automates the same flow with a CI/CD pipeline.
