Lab 5 · IaC
Infra as Code with Skills
Use a HashiCorp Terraform skill to make Bob write better Terraform
Prerequisites
✅ Before You Start
  1. Lab 2 completed, so you have the payment-app-java17 project open in the Bob IDE. If you skipped earlier labs, you can find the Java 17 app here.
  2. Bob is in Advanced mode. Skills require it. We'll also enable auto-approve for Skills so Bob activates them without prompting each time.
  3. Terraform CLI installed locally (terraform -version) so we can run fmt and validate. Need it? Follow Install the Terraform CLI.
💬 OVERVIEW
  • Bob can write Terraform out of the box. But "it runs" is not the same as "it follows the conventions a platform team would accept in review." This lab is a controlled A/B testing: we send Bob the identical prompt twice, the only difference being a HashiCorp Terraform skill loaded on the second run, so any quality jump is attributable to the skill and nothing else.
  • A skill is a reusable instruction set that teaches Bob a specialized workflow. We'll drop HashiCorp's official terraform-style-guide skill into .bob/skills/ and let Bob apply the HashiCorp Terraform Style Guide automatically.
  • To keep the diff readable on screen we provision one small slice: a single bob-demo namespace with a ResourceQuota and a PostgreSQL Deployment, Service, and PVC. Then we prove it's correct with terraform validate, no cluster and no apply required.
  • To judge the difference objectively, we'll ask Bob to evaluate the before and after across concrete quality dimensions the skill is meant to improve: file organization, provider pinning, naming, parameterization, and formatting. For a second opinion, a referee evaluation by a frontier model is provided alongside this lab, in case you're curious how an independent judge scored the same two versions.
Step-by-Step
1
Establish a baseline, no skill yet
First, capture what Bob writes with no extra guidance. Create and send Bob the prompt below. We save this version off to the side so we can compare against it later.
Prompt 5a · Baseline Terraform (no skill)
▼
Write Terraform to provision a single OpenShift namespace for the payment application. Use the hashicorp/kubernetes provider. Provision: - A namespace called bob-demo - A ResourceQuota (requests.cpu 2, limits.cpu 4, requests.memory 4Gi, limits.memory 8Gi) - A PostgreSQL instance: Deployment (postgres:15, single replica) with liveness and readiness probes (pg_isready), a ClusterIP Service on port 5432, and a 5Gi PersistentVolumeClaim Save everything under payment-app-java17/infra/terraform-baseline/. Mark credentials as sensitive and use placeholder values; do not hardcode secrets. Include a .gitignore that excludes Terraform state and the .terraform directory. Do not run or apply any Terraform commands.
ℹ️ Note
You may notice Bob reaches for the hashicorp/kubernetes provider even though we deploy to OpenShift. That's expected and correct: OpenShift is a Kubernetes distribution and exposes the standard Kubernetes API, so the kubernetes provider manages every object we use here (Namespace, ResourceQuota, Deployment, Service, PVC, Secret). Sticking to core k8s resources also keeps the Terraform portable across any cluster. OpenShift-specific objects (Routes, ImageStreams, SecurityContextConstraints, DeploymentConfigs) would need the OpenShift provider instead, and this lab deliberately uses none of them. The reason we can avoid them: PostgreSQL only has to be reachable by the app inside the same cluster, so an internal-only ClusterIP Service is enough. We never need a Route or Ingress to expose it externally, and a Route is exactly the kind of OpenShift-specific object that would otherwise pull us off the kubernetes provider.
2
Notice what's missing
Open payment-app-java17/infra/terraform-baseline/ and skim it with a reviewer's eye. Typical gaps in an unguided generation:
What to review Gap in the baseline Best practice (HashiCorp Style Guide)
Provider / version layout
main.tf		 The terraform and provider blocks sit in main.tf alongside resources. Put settings and provider config in dedicated terraform.tf / providers.tf files so resources stand alone.
Provider pinning
main.tf		 Pinned to older releases (kubernetes ~> 2.23, Terraform >= 1.0). Pin to current versions with the pessimistic operator (~>) so you get patches without surprise majors.
Resource naming
postgresql.tf		 Inconsistent: the PVC is postgres_pvc while the deployment and service are just postgres, repeating the type in one but not the others. Use a consistent noun and do not repeat the resource type in the name (Terraform already namespaces by type). Name all three postgresql.
Parameterization
resource-quota.tf		 Quota CPU/memory values hardcoded in the resource. Lift environment-varying values into input variables with defaults and reference them via var.* (e.g. resource_quota_cpu_limits).
Formatting
main.tf, namespace.tf, postgresql.tf		 Not fmt-clean (trailing whitespace in nested blocks). Keep code canonically formatted; terraform fmt should produce no diff. Use fmt -check -diff to see where.
💡 Tip
The baseline is not broken: its variables are already typed and described, and it passes terraform validate (the command that checks the configuration is syntactically valid and internally consistent, without contacting any cluster). The skill we use in this lab, HashiCorp's terraform-style-guide (one of several Terraform skills in the hashicorp/agent-skills repo), focuses on style and structure, not basic correctness, so that's where the differences will show.
3
Install the HashiCorp Terraform skill
Skills live in .bob/skills/ (project-level) or ~/.bob/skills/ (global). We'll drop HashiCorp's terraform-style-guide skill into the project so it travels with the repo. From a project root, run the following commands in a terminal:
Terminal · Add the skill to .bob/skills/
▼
# From the payment-app-java17 project root mkdir -p .bob/skills # Clone HashiCorp's agent-skills and copy the Terraform style-guide skill in git clone --depth 1 https://github.com/hashicorp/agent-skills /tmp/hashicorp-agent-skills cp -R /tmp/hashicorp-agent-skills/terraform/code-generation/skills/terraform-style-guide \ .bob/skills/terraform-style-guide # Confirm the skill is in place (must contain SKILL.md) ls .bob/skills/terraform-style-guide
A skill is just a folder with a SKILL.md (YAML front matter with name and description, then the instructions) plus any supporting files. Bob reads the description to decide when it applies.

6
Review the comparison
Open payment-app-java17/infra/skill-comparison.md, the file Bob just wrote, and read its table. This is Bob grading its own before and after, so read it the way you'd read any self-assessment: useful, but worth a second opinion.
For a second opinion, we leveraged an independent frontier model as referee to assess the same two directories, with every claim checked against the files and the CLI results reproduced. You can find the result here.
🚀 Tip
The honest takeaway is in both reports: the skill clearly wins on style and structure (formatting, file layout, pinning, naming, parameterization), but it does not guarantee operational completeness with this one skill alone. See the Get More From Agents tip under Going Further below for how to push the first generation closer to production-ready.

Note: your generated artifacts may vary from these reports. Bob is non-deterministic, so the same prompt can yield different file names, structure, and which operational details it includes from run to run. So don't expect an exact match; instead read for the dimensions (file layout, pinning, naming, formatting) rather than the literal values.

To confirm your own output holds up, validate it without touching a cluster: 
cd payment-app-java17/infra/terraform

# proves the code is canonically formatted
terraform fmt -check -recursive

# download providers only, no backend / no cluster
terraform init -backend=false

# check syntax and provider schemas, offline
terraform validate
Expect Success! The configuration is valid. Do not run terraform plan or terraform apply; those reach for a live cluster. Run the same commands against terraform-baseline/ for contrast: it also passes validate (both are valid HCL), but typically fails fmt -check, which is exactly the distinction the skill makes.
Going Further · Production-Ready on the First Pass
🚀 TIP · GET MORE FROM AGENTS
A single skill raises the floor on quality, but it won't cover everything, so you may still spot some operational gaps. The fix is not to babysit every generation, it's to teach an agent your standards once so its next first draft already clears them.
  • Encode your standards, not just style. Pair a style skill with your own skill that bakes in your team's conventions and must-haves, so the agent applies them automatically instead of being reminded each time.
  • Close the loop after every review. When a review catches a gap, add it to the skill so the agent doesn't repeat the mistake. The skill becomes a living, version-controlled checklist your whole team shares.
  • Make acceptance criteria machine-checkable. Tell the agent to run your formatters, validators, linters, tests, and scans, and to fix whatever they flag before declaring the job done. An agent produces stronger first drafts when "done" is an explicit check it can run and verify itself, rather than a subjective sense that the output looks finished.
  • Stack focused skills. Keep each skill small and single-purpose; the agent applies whichever are relevant, and small skills are far easier to review and maintain than one giant prompt.
  • Give the skill a reference file. Drop a checklist or examples file next to the skill with your golden patterns and anti-patterns; the agent reads it to self-check instead of relying on the conversation.
