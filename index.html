Workshop Intro
Examples of how Bob helps across the software delivery lifecycle, from build to Day-2 operations
💬 OVERVIEW
This workshop walks through the complete software delivery lifecycle (SDLC) using IBM Bob, from building a payment processing application in a single prompt, through security scanning, CI/CD pipeline generation, and OpenShift deployment, to the Day-2 SRE operations that drive daily operational toil. Bob drives every stage intelligently, generating production-ready artifacts that can be executed immediately against live OpenShift clusters.
Today you'll get hands-on with 8 labs: Build the App → Java Modernization → Generate Tests → Security Scan → Infra as Code → Deploy to OpenShift → CI/CD Pipeline → Day-2 SRE Ops.

Labs 1–2
Bob Modernizes & Builds the App
  • Analyze a legacy Java 11 codebase and produce a modernization plan — deprecated APIs, effort & risk, recommended order — reviewed before any change
  • Upgrade to Java 17 + Spring Boot 3.x; adopt records, text blocks, pattern matching
  • Build a complete payment app: Spring Boot REST backend, H2 database, cache, transaction-dashboard frontend
  • Deliver the supporting artifacts too: README, Dockerfile, OpenShift manifest
  • Plan-then-execute, with you approving each step
"One spec — Bob modernizes the stack and builds a working, deployable app, plan first."
Java 11→17 Spring Boot 3 Dockerfile OpenShift
🔒
Labs 3–4
Bob Tests & Secures
  • Generate a full JUnit 5 integration suite: happy paths, edge cases, failure scenarios (MockMvc)
  • Measure coverage with JaCoCo against an 80% target and produce a coverage report
  • Run a contextual security analysis — reasoning about code semantics, not just bad strings
  • Produce SecurityScanReport.md: file, line, severity, and a concrete fix per finding
  • Apply the fixes directly in the IDE, no context switching
"Tested and security-reviewed before the code ever leaves your laptop."
JUnit 5 MockMvc JaCoCo Security Scan
⚙️
Lab 5
Bob Generates Infra as Code
  • Generate Terraform to provision the OpenShift namespace and PostgreSQL
  • Apply a HashiCorp Terraform skill so Bob writes style-guide-compliant HCL
  • Pinned providers, typed variables, consistent naming, fmt-clean output
  • Validate locally with terraform fmt and terraform validate — no cluster needed
  • An independent referee evaluation scores the before vs. after
"Infrastructure defined as code — and a skill makes Bob write it the way your platform team would approve."
Terraform Skills OpenShift IaC
🚀
Lab 6
Bob Deploys to
OpenShift
  • Bob generates the oc deployment steps, each command explained
  • Server-side image build on the cluster from the existing multi-stage Dockerfile — no local Docker
  • Deploy into your own deploy-test-<suffix> namespace with an edge (HTTPS) route on port 8081
  • Log in, run the steps, and debug any failures live with Bob
  • Confirm the app is serving via its route before automating
"Deploy manually first to validate the path — then the pipeline automates it."
OpenShift oc CLI Edge Route On-cluster Build
⚙️
Lab 7
Bob Builds the
CI/CD Pipeline
  • Generate a single GitHub Actions pipeline: build, JUnit, OWASP, Semgrep — gates skippable with [skip checks]
  • Build on the cluster with oc, auto-deploy to staging (deploy-test-<suffix>), smoke-test the live route
  • Manual approval gate, then promote the exact image to production with oc tag (deploy-prod-<suffix>)
  • A launch-pipeline.sh wires up secrets, the variable, and the approval gate, and pushes — one command to go live
  • Watch the run end to end, then approve the production deploy
"One spec plus one script — a manual deploy becomes a running, gated delivery pipeline."
GitHub Actions Staging → Prod oc tag Quality Gates
🔧
Lab 8
Bob Assists with
Day-2 SRE Ops
  • Day-2 health check — pod status & restarts, rollout, Service endpoints, route reachability, error logs, resource usage
  • Writes a health report (health-report.md) with a healthy / needs-attention verdict
  • Scales the app out under load to 3 replicas — confirms readiness and Service endpoints
  • Verifies the route keeps serving, then scales back down
  • Validates as it goes, reporting anomalies rather than just firing commands
"Describe the outcome you want — Bob drives the cluster and reports what it sees, instead of you memorizing oc commands."
oc CLI Health Check Scaling Day-2
